# PR #6296 Review

**Title:** feat(interceptor): merge feature pr #3783 into v1.x (custom return type support for interceptor)
**Author:** zhaojjiang
**Base → Head:** axios:v1.x...zhaojjiang:v1.x (0e4f9fa...fdaeb78)
**URL:** https://github.com/axios/axios/pull/6296

## Summary

This PR ports a single-line TypeScript type-definition change from the `main`/`v0.x`/`v2.x` branches into the `v1.x` branch. The change widens the `AxiosInterceptorManager<V>.use()` method signature by introducing an independent type parameter `T` (defaulting to `V`) on the method itself. Before this change the `onFulfilled` callback was constrained to return `V | Promise<V>`, forcing the return type to be identical to the interceptor's input type. After the change the callback may return `T | Promise<T>`, where `T` can be any type the caller chooses. Only `index.d.ts` is touched; no runtime JavaScript is modified.

The diff in full:

```diff
-  use(onFulfilled?: ((value: V) => V | Promise<V>) | null, onRejected?: ((error: any) => any) | null, options?: AxiosInterceptorOptions): number;
+  use<T = V>(onFulfilled?: ((value: V) => T | Promise<T>) | null, onRejected?: ((error: any) => any) | null, options?: AxiosInterceptorOptions): number;
```

## Security Risks

None identified.

The change is confined to a TypeScript declaration file (`index.d.ts`) and has zero impact on runtime behaviour. No input validation, credential handling, XSRF guards, URL construction, or any other security-sensitive code path is touched. Widening a generic type parameter in a `.d.ts` file cannot introduce prototype pollution, unsafe eval, SSRF, XSS vectors, or credential leakage.

## Missing Tests

**Finding: no type-level test was added.**

Because the change is purely a TypeScript type-definition edit, the appropriate test vehicle is a compile-time type test (e.g. a file in `test/typescript/` using `tsd` or a similar type-assertion library). The PR adds no such test. A minimal test should verify:

1. That a request interceptor can return a type different from its input — e.g. `onFulfilled: (config: InternalAxiosRequestConfig) => MyCustomConfig`.
2. That the default (no explicit `T`) still constrains the return type to `V`, preserving the existing behaviour for callers who do not opt in.
3. That the `onRejected` callback signature is unchanged (it already uses `any`, so this is low risk, but worth asserting).

The upstream branches that already carry this change (as referenced in PR #3783) should be checked to see whether they added corresponding type tests; if so, those tests should be ported here as well.

## Breaking Changes

**Potentially source-incompatible for strict downstream TypeScript code, but only in a widening direction.**

- **TypeScript callers that relied on the compiler enforcing `V → V` through the interceptor:** The constraint is now relaxed to `V → T`. This is a widening change (more code is accepted, not less), so it will not break existing callers at the call site.
- **Callers that infer `T` explicitly:** If any downstream code explicitly annotated the `use()` call with a type argument, the semantics of that annotation change slightly, but because `T` defaults to `V` the common unparameterised call form is unaffected.
- **Runtime JavaScript:** Zero impact. The `.d.ts` change is erased at compile time.
- **Node/browser compatibility:** Unaffected.

**Verdict:** Not a breaking change in the traditional sense, but reviewers should be aware that TypeScript's structural typing means a consumer's inferred types for the value flowing *out* of `use()` could silently change if they relied on the narrower `V` bound being enforced. This is an edge case and does not rise to the level of a breaking change.
