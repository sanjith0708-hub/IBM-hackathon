# PR #6402 Review
**Title:** fix(backport): backport security fixes in commits #6167 and #6163 to v0.x
**Author:** Sean-Powell
**Base → Head:** v0.x...fix/backport-1.6.4-security-fixes-to-0.x
**URL:** https://github.com/axios/axios/pull/6402

## Summary

This PR backports two security fixes that were originally landed in axios v1.6.4 (commits #6163 and #6167) to the `v0.x` maintenance branch. The two fixes address distinct vulnerabilities: a **prototype pollution** flaw in `lib/helpers/formDataToJSON.js`, where a crafted FormData key such as `__proto__` could silently overwrite `Object.prototype` properties during JSON construction; and a **credential/header-leakage** vulnerability in the `follow-redirects` dependency (CVE-2023-26159 / CVE-2024-28849), where sensitive headers could be forwarded to untrusted redirect targets. The dependency floor is bumped from `^1.15.0` to `^1.15.4` in `package.json`, and `package-lock.json` is updated to resolve `1.15.6` (the latest patch in that line). Both changes are accompanied by test additions, and the PR was merged by a project maintainer (`jasonsaayman`).

The scope is deliberately minimal — 33 additions and 9 deletions across 5 files — which is appropriate for a security backport. No new features are introduced.

## Security Risks

- **Incomplete prototype-pollution guard (`formDataToJSON.js`):** The patch adds a single check `if (name === '__proto__') return true;` inside `buildPath`. This blocks the direct `__proto__` key but does **not** block the equivalent `constructor.prototype` path. The test itself demonstrates this gap: it asserts that `constructor.prototype.y` ends up as a plain nested object key in the output rather than being discarded. The v1.x fix (commit #6167) added a more comprehensive check covering both `__proto__` and `constructor`; that second guard was not backported here. An attacker who cannot use `__proto__` directly can still reach `Object.prototype` via `constructor[prototype]` keys in a multipart form body.

- **`follow-redirects` minimum version pinned to `^1.15.4`, not `^1.15.6`:** `package.json` sets the floor at `1.15.4`, but `1.15.5` and `1.15.6` contain additional security patches. Because npm's semver resolver will always prefer the latest compatible version in a fresh install this is acceptable in practice, but a consumer running `npm install` against a locked registry mirror or behind a caching proxy could resolve `1.15.4` or `1.15.5` instead of `1.15.6`. Pinning to `^1.15.6` would make the intention unambiguous and prevent inadvertent resolution to still-vulnerable patch versions.

- **No guard against other prototype-pollution spellings:** Key strings like `"__defineGetter__"`, `"__defineSetter__"`, `"__lookupGetter__"`, and `"__lookupSetter__"` are also dangerous in property-assignment contexts. While these are less commonly exploited through FormData payloads, a belt-and-suspenders approach (e.g. `Object.prototype.hasOwnProperty` check or using `Object.create(null)` as the accumulator) would be more robust.

- **No sanitisation of numeric-looking keys that resolve to `__proto__`:** In some JS engines, edge-case numeric coercions or Unicode lookalikes can bypass simple string equality checks. The guard `name === '__proto__'` uses strict equality, which is correct, but a defence-in-depth approach would use an allowlist or `Object.create(null)` rather than a denylist.

## Missing Tests

- **`constructor.prototype` path is not blocked and has no negative-assertion test:** The new test in `test/specs/helpers/formDataToJSON.spec.js` appends `constructor.prototype.y = 'value'` but then *asserts it appears in the output* as a nested object. There is no test asserting that `({}).y` remains `undefined`, nor a test that confirms `constructor.prototype` keys are dropped the same way `__proto__` keys are. This is consistent with the incomplete fix, but a future PR that tightens the guard will have no regression coverage for the `constructor.prototype` vector today.

- **No test for deeply nested `__proto__` traversal:** The test only checks a single-level `__proto__` key. There is no coverage for `a[__proto__][polluted]` style nested paths, which could exploit the recursive `buildPath` call with a non-root `__proto__` segment.

- **No test verifying array targets are not polluted:** The test covers plain-object targets. There is no test asserting that an array-valued path containing `__proto__` (e.g. `foo[0][__proto__].bar`) cannot pollute `Array.prototype`.

- **`follow-redirects` upgrade is not integration-tested:** The `test/unit/adapters/http.js` change updates the expected error message string (`'Redirected request failed: Provided path is not allowed'`) to match the new `follow-redirects` 1.15.6 wording, which is correct. However, there is no test covering the _header-stripping_ behaviour introduced in `follow-redirects` >= 1.15.4 (the fix for CVE-2024-28849). A test that fires a redirect to a different origin and confirms that `Authorization` / `Cookie` headers are not forwarded would close that gap.

## Breaking Changes

- **Changed error message string in redirect path:** `follow-redirects` 1.15.6 changes the text of the "path not allowed" error from `'Provided path is not allowed'` to `'Redirected request failed: Provided path is not allowed'`. The test in `test/unit/adapters/http.js` is updated accordingly, but any v0.x consumer who is currently `catch`-ing and string-matching against the old error message (`error.message === 'Provided path is not allowed'`) will silently stop matching after this upgrade. This is a subtle behavioural breaking change introduced by the dependency upgrade. It should be documented in the `CHANGELOG` or release notes for the patch version that ships this fix.

- **`formDataToJSON` now silently drops `__proto__` keys:** Previously a FormData entry with the key `__proto__` would be processed (and potentially pollute the prototype). After this patch it is silently ignored (the recursive walk returns `true` and the key is skipped). Code that deliberately passed `__proto__` as a field name (unlikely, but possible) will see the field disappear from the resulting object. This is the intended security fix, but it is a behaviour change and should be noted in the changelog.

- **No changes to exported types or public API surface** — the `index.d.ts` type definitions are untouched, and no public function signatures are altered. For consumers who only call the documented API, there are no breaking changes.

## Suggested Improvements

- Extend the `__proto__` guard to also cover `constructor`, mirroring the complete v1.x fix.

  **Code Fix:**

  ```js
  // lib/helpers/formDataToJSON.js — inside buildPath
  if (name === '__proto__' || name === 'constructor') return true;
  ```

- Use `Object.create(null)` as the accumulator to eliminate the prototype chain entirely, making the denylist a second line of defence rather than the first.

  **Code Fix:**

  ```js
  // lib/helpers/formDataToJSON.js
  export default function formDataToJSON(formData) {
    const obj = Object.create(null); // ← was {}
    // ... rest of implementation
    return obj;
  }
  ```

- Bump the `follow-redirects` floor to `^1.15.6` in `package.json`.

  **Code Fix:**

  ```json
  "follow-redirects": "^1.15.6"
  ```

- Add a `CHANGELOG.md` entry covering both CVEs for v0.x users.

  **Code Fix:**

  ```markdown
  ### Security

  - Fixed prototype pollution vulnerability in `formDataToJSON` (`__proto__` and
    `constructor` keys are now silently dropped). Ref: commit #6167.
  - Updated `follow-redirects` to ≥1.15.6 to address CVE-2024-28849
    (Authorization/Proxy-Authorization header leakage on cross-origin redirects).
  ```

- Add negative assertion tests for both the `__proto__` and `constructor.prototype` vectors.

  **Code Fix:**

  ```js
  // tests/specs/helpers/formDataToJSON.spec.js
  it('drops __proto__ keys without polluting Object.prototype', () => {
    const fd = new FormData();
    fd.append('__proto__[polluted]', 'yes');
    formDataToJSON(fd);
    expect(({}).polluted).toBeUndefined();
  });

  it('drops constructor.prototype keys without polluting Object.prototype', () => {
    const fd = new FormData();
    fd.append('constructor[prototype][polluted]', 'yes');
    formDataToJSON(fd);
    expect(({}).polluted).toBeUndefined();
  });
  ```

## Overall Assessment

**Request Changes** — The PR is well-intentioned and the `follow-redirects` bump is straightforwardly correct, but the prototype-pollution fix is incomplete: the `constructor.prototype` attack vector remains open and the accompanying test inadvertently documents the gap rather than closing it. The minimum required change before merging is to extend the guard to cover `constructor` (matching the v1.x fix) and add a negative assertion for `({}).y`. The missing changelog entry and the subtle error-message breaking change from the dependency bump should also be addressed before tagging a v0.x patch release.
